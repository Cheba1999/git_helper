## 1. Инициализация локального репозитория.
### 1. Создать дирректорию на вашем ПК в удобном для вас месте.
* mkdir my_person_project


### 2. Перейти в данную дирректорию.
* cd ./my_person_project


### 3. Инициализировать локальный Git-репозиторий.
* git init

-------------------------------------------------------------------------------

## 2. Создание файлов и редактирование файлов.
### 1. Создать непосредственно файл.
* touch my_prjct.cpp


### 2. Редакторивать и заполнить файл.
* nano my_prjct.cpp  
Или в моём случае я использую alias для notepad++:
* notepad++ my_prjct.cpp


### 3. Сохранить буфер обмена.
* для каждой программы по своему.

-------------------------------------------------------------------------------

## 3. Выборка файлов на подготовку к созданию коммита.
Выбрать файлы для подготовки.
* git add my_prjct.cpp  
Или:
* git add --all

## 4. Создание коммита.
Просто прописать команду:
* git commit -m "Ваше комментарий-метка",  
где флаг -m позволяет добавить ваш личный комментарий.
В комментарие лучше писать метку, отображающую контекст изменений.

### 1. Глобальный файл настроек.
Гит имеет свой глобальный файл конфигурации.
Он находится в папке профиля пользователя (актуально для Windows).
К нему можно обратить, используя следующую лексическую конструкци:

, после которой вы можете прописать данные, которые хотите изменить.


### 2. Локальный файл настроек.
Так же можно менять файл кофигурации внутри самого локального
Git-репозитория. Команда обращения схожа:
* git config --local  
Примеры можно увидеть ниже.

## 9. Дополнительные настройки.
Текст-сумбур.
Может возникнуть проблема.
На виндовс окончание строки кончается при помощи последовательности CRLN (\r\n).
Это комбинация спец. символов, которые отвечают за две вещи:
- перевод каретки в начало,
- перевод строки на новую.
В линуксе используется просто LF (\n).
Если редактировать текст в nano, а именно внутри Git Bash, то оный сохранит
программу в Линукс формате (LF).
Поэтому, что бы избежать конфликты:
1. Мусор в истории: Гит считал бы, что мы изменили каждую строку файла (из-за невидимых символов), даже если ты просто исправили одну букву.

2. Конфликты: Если бы мы работали с кем-то, у кого Linux/Mac, ваши файлы постоянно «воевали» бы за формат переноса строки, ломая сравнение версий. 
Используем команду:
* git config --global core.autocrlf true
Это команда для изменения этой настройки в глобальном конфиге.

То есть, гит берёт и удаляет CR, только потом сохраняет файл.
А при скачивании, наоборот, подставляет CR.

## 10. Загрузка коммита на удалённый репозиторий.
### 1. Связать локальный репозиторий с удалённым.
Если ты еще не указывал Гиту, куда именно отправлять файлы, нужно добавить адрес (remote). Делается это один раз для проекта:
* git remote add origin git@github.com:ИМЯ_ПОЛЬЗОВАТЕЛЯ/ИМЯ_РЕПОЗИТОРИЯ.git

Здесь origin — это стандартное имя для удалённого сервера.


### 2. Отправить изменения (Push).
Чтобы твои коммиты «улетели» из твоего ПК на GitHub, используй команду:
* git push -u origin main

Флаг -u связывает твою локальную ветку main с веткой на сервере. В следующий раз можно будет писать просто:
* git push

## 11. Хеш — идентификатор коммита.
### 1. Что такое Хеш?
Хеширование — это способ преобразовать
набор данных и получить их «отпечаток» (англ. fingerprint).

Git хеширует (преобразует) информацию о коммите с помощью алгоритма SHA-1
и получает для каждого коммита свой уникальный хеш — результат хеширования.

Обычно хеш — это короткая (40 символов в случае SHA-1) строка, которая
состоит из цифр 0—9 и латинских букв A—F (неважно, заглавных или строчных).

Она обладает следующими важными свойствами:
* если хеш получить дважды для одного и того же набора входных данных, то результат будет гарантированно одинаковый;
* если хоть что-то в исходных данных поменяется (хотя бы один символ), то хеш тоже изменится (причём сильно).


### 2. Хеш — основной идентификатор коммита.
Хеш — основной идентификатор коммита и позволяет узнать его автора, дату и содержимое закоммиченных файлов.
Все хеши, а также таблицу соответствий хеш → информация о коммите Git хранит в папке .git.

## 12. Логи.
### 1. Обычный лог.
* git log

Выводит текст следующего формата:
```
commit e83c5163316f89bfbde7d9ab23ca2e25604af290
Author: Linus Torvalds <torvalds@linux-foundation.org>
Date:   Thu Apr 7 15:13:13 2005 -0700

    Initial revision of "git", the information manager from hell
```

Разберём элементы, из которых состоит описание:

1) строка из цифр и латинских букв после слова commit — это хеш коммита;
2) Author — имя автора и его электронная почта;
3) Date — дата и время создания коммита;
4) в конце находится сообщение коммита.


### 2. Сокращённый лог.
* git log --oneline


Выводит текст следующего формата:
```
user@computer:~/dev/first-project$ git log --oneline
e007f50 (HEAD -> master) Добавить амбиций в список дел
090e96e Добавить описание проекта в readme
baa3b6e Мой первый коммит!
user@computer:~/dev/first-project$
```

Сокращённый хеш (то есть первые несколько символов полного) можно использовать точно так же, как и полный.
Для этого команда git log --oneline автоматически подбирает такую длину сокращённых хешей,
чтобы они были уникальными в пределах репозитория и Git всегда мог понять, о каком коммите идёт речь.

## 13. HEAD.
1. При вызове команды git log рядом с последним коммитом появляется надпись (HEAD -> main).
2. Файл HEAD указывает на коммит, который сделан последним (то есть на самый новый).
3. Если открыть просмотреть содержание файла, можно наблюдать следующее:
```
$ cat HEAD # команда cat показывает содержимое файла
ref: refs/heads/master # в файле вот такая ссылка
```

4. Внутри HEAD — ссылка на служебный файл: refs/heads/master (или refs/heads/main).
5. Если заглянуть в этот файл, можно увидеть хеш последнего коммита.
```
$ cat refs/heads/master # взяли ссылку из файла HEAD
# внутри хеш
e007f5035f113f9abca78fe2149c593959da5eb7

$ git log 
# сверяем с хешем последнего коммита
commit e007f5035f113f9abca78fe2149c593959da5eb7
Author: John Doe <johndoe@example.com>
Date:   Tue Mar 28 00:26:53 2023 +0300
```
6. Вместо хеша последнего коммита можно написать слово HEAD — Git поймёт

## 14. Статус файлов.
В кратце ситуацию можно описать так:
* неотслеживаемые (untracked),
* отслеживаемые (tracked).

1. Сразу после создания файл находится в статусе untracked.
2. После добавления файла на подготовку к коммиту он попадает в статус tracked.
3. Далее файлы в tracked могут иметь следующие статусы:
* staged,
* modified.
4. Если к файлу применили команду git add ИМЯ_ФАЙЛА, то он становится staged.
5. Если файл просто тредактировали, но не применили команду git add ИМЯ_ФАЙЛА, он становится modified.
6. Если файл после команды git add ИМЯ_ФАЙЛА отредактировали, то к нему применяются два статуса: staged и modified.
7. Если файл отредактировали, добавили на готовность к комиту и закомитили, то он лишается статусов staged и modified.
И просто остаётся в состоянии tracked. При вызове статуса такие файлы не отображаются. Остальные отображаются. Это очень удобно.

## 15. Оформление сообщений к коммитам.
### Conventional Commits.
Стандарт Conventional Commits отличается качественной документацией и подробной проработкой.
Он подходит для репозиториев с исходным кодом программ.
Conventional Commits предлагает такой формат коммита: <type>: <сообщение>. 
Первая часть type — это тип изменений. Таких типов достаточно много. Вот два примера:
feat (сокращение от англ. feature) — для новой функциональности;
fix (от англ. «исправить», «устранить») — для исправленных ошибок.
Более подробный список можно увидеть на сайте с описанием этого стиля.
https://www.conventionalcommits.org/ru/v1.0.0-beta.4/#спецификация
Например, сообщение может быть таким.

```
git commit -m "feat: добавить подсчёт суммы заказов за неделю" 
```


### GitHub-стиль.
GitHub можно использовать не только для хранения файлов проекта, но и для ведения списка задач (англ. issue) этого проекта. Если коммит «закрывает» или «решает» какую-то задачу, то в его сообщении удобно указывать ссылку на неё. Для этого в любом месте сообщения нужно указать #<номер задачи>. Например, вот так.

```
$ git commit -m "Исправить #334, добавить график температуры" 
```

В таком случае GitHub свяжет коммит и задачу.

```
💡 Инфинитив и императив
Для сообщений на русском языке часто рекомендуют использовать инфинитивы. Например: Добавить тесты для PipkaService, Исправить ошибку #123 и так далее.
Для сообщений на английском рекомендуется использовать повелительное наклонение (англ. imperative). Например: Use library mega_lib_300, Fix exit button и так далее.
Эти рекомендации сложились исторически, и им следуют многие проекты.
```
